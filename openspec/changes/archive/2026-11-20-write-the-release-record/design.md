## Context

The draft Change `decide-before-heavy-work` leaves a film's release documents to a later Change; its decision 21 states what a release's record is for. This Change admits the part that writes the record. Its proposal states why and what changes; its specs state the behavior. This design records how the slice is built and what stays in the draft. A mark such as [S2] names an entry under Sources.

What the engine holds, read at `db7a837` (0.24.1) on 20 November 2026 [S1]:

- `delivery/reproduction.py` defines the manifest (`Release`: version, each edition's soundtrack and stage digests and its films' PSNR floors, the film-bound sources, the assets), the asset names of an edition (`members`), the checksums format and `load`, which refuses a manifest that does not name exactly what the editions publish. The same module compares a rebuild with the published assets in `build/artifacts/release/`. A release's asset names carry no version.
- The film verifier checks an edition in phases: its bound inputs (sources, narration custody, both pictures, the package records), the decode of its four films, Spotlight, and its recorded review. On the trial build the bound inputs took 0.7 s an edition and the decode 32 to 35 s [S4]. A review record that is missing ends the verifier in a traceback, not a refusal.
- The picture check binds the captioned picture's render to its staged document. An uncaptioned picture that is derived from the captioned one, as under the capture all three films declare, has a receipt without a stage, and nothing checks its staged document after the render; `rendering.require_current_stage` checks a stage against its sources before one.
- A delivery fills the film's own folder, which the host's rules name, or a folder the caller names; every checkout of a film delivers to the same own folder. Its readback states the folder and, since 0.23.0, the rule that gave it.

What the films' kit holds, read the same day [S2]: one script that copies each member into the release folder under its release name and refuses a folder that is not empty, and one that writes the manifest. The second refuses unless the recorded reviews bind the current films, both staged documents equal their render receipts' sources, the soundtrack equals its assembly record, the delivery's readback matches and names the film's own folder, and each staged film equals its delivered file. It takes the sources' paths from the film's format policy, the version from `VERSION`, and every film's floor from an option whose default is 45.0. It imports `filmkit.delivery.documents_folder`, which 0.23.0 renamed, and its check of the uncaptioned stage asks a derived receipt for a field it does not hold. Another kit script treats the release folder as the copy of a release's films on this disk before it removes them from a forge's page.

Each of the three films' current records names two editions, 20 film-bound sources and 21 assets, and states 45.0 dB for each of its eight films [S3].

## Goals / Non-Goals

**Goals:**

- A film records a release with one engine command and no script of its own.
- The record is written only from a build that was reviewed and that the film's own delivery folder holds, and each of those facts is asked of the module that owns it.
- No film's released record or bytes change; a record written again from the same build is the same record.

**Non-Goals:**

- A new manifest. The model and the comparison keep every field and rule they have.
- Publishing. The command reaches no network and writes nothing outside the film's repository.
- Writing a film's Changelog, README or notices.
- Naming every refusal in one run. Each check takes seconds, so the first refusal stops the command. Stated sources that are refused for different reasons are named one reason a run: the reason of the first of them in sorted order, with every path refused for that reason.

## Decisions

Each decision states what it rests on, what was considered, why the option taken was chosen, and where it applies. A decision of the draft is cited by its number there.

1. **The writer is a module beside the comparison and reads the record's definitions where they are.**
   - **Rests on:** the manifest's definitions stand in the module that compares a rebuild [S1]. Three engine test files, each film's manifest test and comparison task, and three kit scripts reach them there by name [S1] [S2] [S3]. The writer has to load the verifier, which already loads every module the comparison loads [S1].
   - **Considered:** (a) the writer inside `reproduction.py`, one module that reads, writes and compares: the two hold 366 and 267 effective lines by ETHOS's measure as they stand, together over the ceiling of 500 that measure holds a module to; (b) a writer module, `delivery/release.py`, that imports the definitions from the comparison; (c) moving the definitions into the writer's module and having the comparison import them.
   - **Chosen because:** (b). It moves nothing a film, a test or a script reaches today, and (c)'s gain, a module for the record alone, costs every importer for no behavior.
   - **Applies to:** `delivery/release.py`, which refuses with the manifest's own error. `delivery/reproduction.py` gives the rules of `load` as a check of a record that is not yet written.
   - **Reopened when:** the comparison's local reference for a release's films (the draft's decision 21) is built.
2. **One command writes the record, and it asks each fact of its owner.**
   - **Rests on:** the kit's writer compares the staged documents with their render receipts and the soundtrack with its assembly record itself; the verifier's narration and picture checks hold the soundtrack's and the captioned stage's bindings, and no check holds a derived picture's uncaptioned stage after the render [S1] [S2]. The verifier's bound-input phase takes 0.7 s an edition [S4].
   - **Considered:** (a) restating the bindings in the writer, as the kit does; (b) requiring a full verification first, a decode of eight films for facts the delivery task has already established; (c) the writer calls the verifier's checks of the bound inputs and of the review, and the staging's check of each stage the record names.
   - **Chosen because:** (c). A binding has one definition, and the writer stays light.
   - **Applies to:** `delivery/verification.py`: the checks of an edition's bound inputs and of its review are callable without the decode, and a missing review record is a refusal by name; the verifier's own command runs them as it does today. `delivery/release.py` asks them for each edition, then `rendering.require_current_stage` for the uncaptioned stage where the record names it; the captioned stage is asked by the verifier's picture check already. The first refusal stops the command in one line: the owner's words after the edition and, for a stage, the picture. A film's chain therefore keeps staging its uncaptioned picture, as the films' and the sample's chains do [S1].
3. **A release is recorded from the build the film's own delivery folder holds now.**
   - **Rests on:** the kit refuses a readback of another folder than the film's, as a preview's is, and a staged film that differs from its delivered file [S2]. A readback is a record of one moment: it can come from an engine that stated no rule, from a host root that has changed since, or from before another checkout delivered to the same folder [S1].
   - **Considered:** (a) binding the record to the review alone, with delivery left to the film's task order; (b) reading the readback's folder, rule and member digests; (c) comparing every delivery member in the film's own folder, as the host names it when the command runs, with the build's file.
   - **Chosen because:** (c). It states what the release needs, that the films the record names can be watched where the film says they are, and it reads the folder, not a record about it. Hashing the members costs seconds.
   - **Applies to:** `delivery/folder.py` gives the comparison of a folder's members with the build's; `delivery/release.py` asks it of `delivery_destination()` with no folder named. A member that is missing or holds other bytes is refused by its path, and a folder the delivery module itself refuses to name, such as a host root that is no absolute path, is refused in its words.
4. **Each film keeps the floor its record states.**
   - **Rests on:** the manifest owns each film's PSNR floor, and the comparison reports a film without one as calibrating [S1]. The kit writes its option's default, 45.0, for every film at every release [S2], and each of the three films' current records states 45.0 for every film [S3]. A film has the same asset name from one record to the next [S1].
   - **Considered:** (a) an option with a default, the kit's form, a number in code; (b) a declaration in `content/film.toml`, a second owner of a value the manifest already owns, and a change in each film; (c) the floor of a film the replaced record names is carried, and a film it does not name gets none.
   - **Chosen because:** (c). The value keeps its one owner and no number enters the engine. A film changes a floor where it is stated, in its record, before its proof.
   - **Applies to:** `delivery/release.py`. The replaced record is read by the manifest's model alone, not by `load`'s rules, so a record whose asset names changed still gives its floors. A tracked record the model itself refuses stops the command by name: its floors are a person's to repair or to state again after removing it. The command prints each film's floor or that it has none, in a dry run too.
   - **Reopened when:** a film's first release is recorded by this command, or a film wants one floor stated for all its films.
5. **The film-bound sources are stated at every run, by the film's task from the film's one declaration of them.**
   - **Rests on:** the rule that design principles are hard requirements [S7]: each fact has one source; what repeats it is derived from that source, never maintained beside it; and a check that refuses a disagreement afterwards is not a source. The record lists each tracked file that no formatter rewrites and whose bytes the published films' build reads [S1]. Which files those are is declared once, in the film: each of the three films declares them in its format policy, and tests that its record lists exactly them [S3]. The kit reads the film's format policy for the paths at each release [S2].
   - **Considered:** (a) the engine reading the film's format policy, which is another product's configuration and which the engine does not parse; (b) the paths of the replaced record carried forward and hashed again, with `--sources` for a first record or a change and the film's test comparing the record's list with the policy afterwards, which this design first held and which the rule excludes: the carried list is a second copy kept beside the declaration, and the test is a check afterwards; (c) a list in `content/film.toml`, a second hand-kept copy beside the policy; (d) the paths stated at every run by the film's task, which derives them from the film's one declaration when it calls the command.
   - **Chosen because:** (d). The declaration stays the one source: the record's list is derived from it at each run, and no list stands beside it that could differ. The engine parses no other product's configuration and holds no film's list.
   - **Applies to:** `delivery/release.py`. `--sources` is required at every run, and the command takes no source from the record it replaces, which it reads for the floors alone. The paths are recorded in sorted order, each once. A stated path that the manifest's model does not list (`reproduction.SourcePath`) is refused in words that name the model and print its pattern: the rule is stated in the model alone, and no text words it by hand. A stated source is a file below the film's root that is not the record and does not lie below the folder that holds what the engine generates, and that no link leads to either or outside the root; any other is refused by name. Those are the checks, and no more: the paths are compared as they are spelled, so the record or that folder in another letter case, on a volume that folds case, and a hard link to either are recorded as stated, and nothing asks whether a file is tracked, since which files are film-bound is the film's declaration. No engine module names that folder by itself; the command takes it as the first name of the release folder's path, which `reproduction` states, until one owner names it. A stated source that is not a file is refused by name. Beside the version line the command prints each path the replaced record listed that the run does not state and each the run states that it did not list, in a dry run too: with the film's comparing test gone this is the one place a list that shrank is seen, and it is a report and no second source, so nothing is refused for it.
6. **The release folder is staged beside itself and not overwritten with other bytes unless the caller says so.**
   - **Rests on:** the comparison and the films' senders read the published assets from `build/artifacts/release/` under their release names and refuse one that differs from the manifest [S1] [S2]. Asset names carry no version, so the next release's films have the names of this one's, and that folder can hold the only copy of a release's films on the disk [S2]. The kit refuses a folder that is not empty [S2].
   - **Considered:** (a) writing the manifest alone and leaving the folder to a second step; (b) making the folder hold exactly the new assets, which silently replaces another release's films; (c) refusing a folder that holds any entry but the bytes the record would write, unless the caller passes `--replace`; staging the whole set in a sibling folder; putting it in the folder's place; writing the manifest last.
   - **Chosen because:** (c). The engine can know whether the folder's bytes are the record's; whether other bytes are still wanted, only the caller knows, so the caller says it. A record written again before its tag, after a review was recorded again or an edition rebuilt, is the same case as the last release's films: other bytes under the same names.
   - **Applies to:** `delivery/release.py`. The record is checked by `load`'s rules before any file is written. A folder that already holds exactly the record's assets is left as it is. Otherwise the assets are staged whole in `build/artifacts/release.staging/`, which a run removes first where an interrupted run left it, each on macOS with the system's own `/bin/cp -c`, a clone where the file system clones and a copy elsewhere, named by its path since a `cp` that `PATH` holds first may refuse the option, and on another platform, whose `cp` has no such option, with a copy that keeps the file's times; then the folder is removed and the staged one renamed to it. A release path or a sibling path that is a link or no folder is refused by its path, with `--replace` too. Finder's `.DS_Store` is no entry, as in a delivery. A refusal, and a failure while staging, leave the folder and the tracked manifest as they were. A run that stops in its last two steps, after the folder was removed or before the manifest was written, leaves the manifest as it was, and the next run completes the record without `--replace`. `--dry-run` prints the record and changes no file.
7. **The command says which record it replaces, and refuses a version the manifest cannot state.**
   - **Rests on:** the manifest's version takes three numbers and no pre-release, while a film's `VERSION` may hold one [S1]. A record of the version already recorded is written again legitimately before its tag: `review.round record` stamps the review record, which is a release asset, each time it runs, and a proof can reopen an edition [S1]. The replaced manifest cannot tell a released record from this release's own earlier one.
   - **Considered:** refusing the same version with other assets, which refuses those cases and leaves a hand edit of the tracked record as the only way on.
   - **Chosen because:** the engine states what it can know: the version it replaces and the version it writes. Whether that version is released is the tag's to say.
   - **Applies to:** `delivery/release.py` refuses a `VERSION` the manifest cannot state, by name, and prints the replaced record's version beside the new one, in a dry run too.

No engine command reads a page's set today. They are admitted together with the proof task, which each edition released from December owes.

## Risks / Trade-offs

- A carried floor is never looked at again. → It is the film's stated standard, as it is today; the comparison reports every film's minimum beside it at each proof, and the command prints the floors it carries.
- A film that does not deliver to its own folder cannot record a release. → Intended: decision 3.
- A film whose release folder holds the last release's assets, or this release's earlier ones, must say `--replace`. → The refusal names the entries and the option; a film's task that always passes it gives up the protection knowingly.
- Staging copies several gigabytes where the file system does not clone. → The films build on Apple silicon, whose file system clones.
- The command's first run for a release is the first edition released with it. → Each refusal is tested on a built tree; the three films' tracked records are written again from their own values and compared byte for byte; and the command runs whole on a real film's build before this Change lands: the essentials film's trial build of 19 November 2026, read with the environment that built it, is delivered, recorded, compared with its record and recorded a second time (task 3.2).

## Migration

A film adds one task that calls the command after its delivery; its two kit scripts are no longer called. The task names the paths the film's format policy declares as immutable carriers, by reading that policy when it runs, so the record's list is derived from the declaration at each release and kept nowhere beside it. The film's test that compared the record's list with the policy goes with the copy it guarded. Its record and its released assets stay as they are. The first record a film writes with the command carries its floors from the record it replaces.

## Open Questions

- Whether a film's floor should be its declaration and not its record's. Decision 4 states what reopens it.
- Where the reading of a film's format policy stands. A film's task reads the policy and states the paths (Migration), the same lines in each of the three films. ETHOS has no command that prints the paths a format policy declares for one owner, and plans none [S8]. One reader in the engine, as an added option of this command, would state those lines once; it is left for the release in which the films adopt the command, and the command's present form stays valid beside it.
